Locking Down Copilot Connectors Without Breaking Anything

Nov 12, 2026 · Chad Cox

How to move from "everything on" to "approved only" in the Microsoft 365 admin center, what you can automate today, and where the API still falls short.

The problem: everything is on by default

Open the Microsoft 365 admin center in a typical Copilot tenant and you will find hundreds of agents, plugins, MCP servers and connectors, many of them set to "All users". In one recent review, the Tools registry listed 470 plugins and 458 MCP servers, and the Copilot Connectors page showed dozens of third-party connections in a Ready state. Nobody had approved most of them individually; they were simply available.

The instinct is to "block everything". In practice there is no single block-all button, and blocking blindly risks cutting people off from tools they rely on. A better pattern is to measure usage first, keep what is needed, and restrict the rest to approved groups.

A four-step pattern that works

1. Measure before you change anything

Start with the usage reports, not the settings. Under Reports > Usage > Microsoft Copilot, the Connectors report shows connections used by Copilot and by agents, active connector users and connector responses over 7 or 30 days. The Agents report shows active users and active agents. In our review every number was zero, which meant restricting access would not interrupt anyone.

Treat a zero carefully. The Connectors report is in preview, it only looks back 30 days, and it does not yet count usage inside Cowork. Zero means "no recent measured use", not "never needed".

2. Set an outer boundary with groups

Agents > Settings > User access controls who can use any agent or plugin at all. Changing it from "All users" to "Specific users or groups" is the single most powerful step, because everything else is limited by it. We used six security groups: one SuperUsers group plus five department groups (Revenue, Finance, People, Technology and Operations).

Confirm the groups have the right members before you save. Anyone outside them loses access immediately.

3. Assign each approved tool to the right groups

Each plugin under Agents > Tools has a Users tab with three options: All users, No users, or Specific users and groups. Each Copilot connection has an equivalent "Add staging" option. Give your SuperUsers group every approved item, then add the department that actually needs it. Leave items that are already set to "No users" alone; switching them to a group turns them on.

4. Block what you never want

Some tools should be off for everyone. Blocking an MCP server under Agents > Tools > MCP servers also blocks its linked plugins and connectors, and the confirmation dialog lists them. We blocked Google Drive, Google Calendar, Google Sheets, Google Tasks and Google Contacts this way. Note that there was no item called "Google Docs"; Docs files are reached through Google Drive, so check what a name actually covers before assuming it is missing.

Finally, users can still see restricted plugins and choose Request access. Those requests land under Agents > Tools > Requests, which becomes your ongoing approval queue.

Can this be automated?

Partly. Microsoft has published the Agent 365 Package Management API in Microsoft Graph. It treats each agent, plugin, MCP server or skill as a "package" and offers these operations:

Operation Endpoint Status
List packages GET /copilot/admin/catalog/packages Available
Get package details GET /copilot/admin/catalog/packages/{id} Available
Update package metadata PATCH /copilot/admin/catalog/packages/{id} Preview
Block a package POST /copilot/admin/catalog/packages/{id}/block Preview
Unblock a package POST /copilot/admin/catalog/packages/{id}/unblock Preview
Reassign ownership POST /copilot/admin/catalog/packages/{id}/reassign Preview

That covers inventory, blocking and ownership well. Pulling a full list of tools, filtering by type or last-updated date, and blocking a known list of unwanted items can all be scripted.

Why the API is not 100% yet

Before you plan a fully scripted rollout, be honest about the gaps:

  • The write operations (block, unblock, update, reassign) are in preview, so behavior and shape can change before general availability.

  • Using the API requires a Microsoft Agent 365 license and the AI Administrator role.

  • By default, listing packages returns only items that contain an agent. You must filter on element type to see plugins, MCP servers and skills.

  • The API does not return Power Platform connectors.

  • In Microsoft's published operation list, there is no endpoint for the organization-wide User access setting, the Agent and plugin access publisher categories, per-plugin "Specific users and groups" assignment, or connector staged rollout. Those steps, which were the heart of our group-based approach, still had to be done in the admin center.

  • The usage reports that should drive your decisions are preview, short-window and missing Cowork activity.

In short, the API can tell you what you have and switch individual items off. It cannot yet express "only these groups may use this tool", which is where most of the governance value lives.

Permissions you need (least privilege)

None of this needs Global Administrator. The AI Administrator role is built for exactly this work: it covers Copilot settings, agents, plugins, MCP servers and skills, usage reports and most tenant-wide consent, without broad control over the rest of Microsoft 365. Two cautions. Microsoft notes the AI Administrator role is still being expanded, so test each step with it before assuming Global Administrator is required. And treat it as the privileged role it is: assign it through Privileged Identity Management so it is activated just in time, with MFA, only for the governance session.

Here is the smallest role that can do each part of the job:

Task Least-privileged role Notes
Read the Connectors and Agents usage reports AI Administrator Reports Reader can read the Copilot usage report APIs if you only need data.
Set Agents > Settings > User access to specific groups AI Administrator Organization-wide boundary for agents and plugins.
Assign groups on each plugin, and block or unblock plugins and MCP servers AI Administrator Done from Agents > Tools.
Approve MCP server requests and grant tenant-wide consent AI Administrator Apps that need Microsoft Graph application permissions still need Global Administrator or Privileged Role Administrator.
Create the SG-Copilot groups and manage membership Groups Administrator Group owners can maintain membership day to day.
Read-only review of the setup AI Reader or Global Reader Cannot change any setting.
Search the audit log for Copilot and Cowork activity Audit Reader (Microsoft Purview) Every Cowork browser task is logged in the unified audit log.
Script inventory or blocking with the Package Management API AI Administrator plus an Agent 365 license CopilotPackages.Read.All for inventory, CopilotPackages.ReadWrite.All to block. Granting a Graph application permission is a one-time Global Administrator or Privileged Role Administrator consent.

Bridging the gap with Copilot

Where the API stops, an AI assistant that can work the admin center for you fills in. Copilot can read the usage reports, walk the Tools registry, apply group assignments item by item, confirm each "updated successfully" message and write up a report as it goes. It is slower than an API call, and it should pause for your confirmation on anything that blocks or broadens access, but it removes hours of repetitive clicking and leaves an audit trail.

What Cowork needs before it can do the clicking

Cowork drives the admin center through Microsoft Edge on your own device, signed in as you. It has the same reach you do, never more, so the permissions above still decide what it can change. Put these in place first:

  • Cowork itself: the admin account needs a Microsoft 365 Copilot license and access to Cowork in your tenant (including the Anthropic subprocessor setting where your region requires it).

  • Cowork browsing turned on: it is off by default. An admin enables it under Copilot > Settings > View all > Cowork settings > Allow browser access, and can limit it to specific security groups, such as your admin group.

  • Cowork running in a browser: browser tasks are not supported in the desktop app or on mobile.

  • Microsoft Edge 152.0.4191.53 or later installed (it does not need to be the default browser), signed in with the same work account you use for Cowork. InPrivate and guest windows do not work.

  • Edge policy, if you manage Edge centrally: the CopilotCoworkToolActionsEnabled policy controls whether Cowork may take actions in Edge. Enable it for your admin devices or profiles.

  • First-run consent: the first time Cowork needs the browser, select I understand in the conversation.

  • The right role, activated: activate AI Administrator (and Groups Administrator if the session will touch group membership) in PIM before you start. If Cowork hits a permission error, it should stop and report it rather than look for another route.

  • Sign-in prompts: Conditional Access and MFA still apply. When a prompt appears, Cowork hands control back to you to complete it.

Because the session runs as you, every change is attributed to your account, and each Cowork browser task is recorded in the unified audit log. Search it in Microsoft Purview with the Audit Reader role.

Sample prompt

Copy and adapt this prompt:

Open the Microsoft 365 admin center and help me move Copilot agents, plugins, MCP servers, skills and connectors to an approved-only model. I am signed in with the AI Administrator role activated; if any page says I lack permission, stop and tell me rather than trying another way. Do this in order and pause for my approval before any change:

  1. Read-only: pull the Copilot Connectors and Agents usage reports for the last 30 days and list every plugin, MCP server, skill and Copilot connection with its current status and who it is available to. Save this as a spreadsheet.

  2. Set Agents > Settings > User access to Specific users or groups using these groups: SG-Copilot-SuperUsers, SG-Copilot-Revenue-Bronze, SG-Copilot-Finance-Bronze, SG-Copilot-People-Bronze, SG-Copilot-Technology-Bronze and SG-Copilot-Operations-Bronze.

  3. For every item that is currently Available, change it from All users to SG-Copilot-SuperUsers plus the department group I assign in the spreadsheet. Do not turn on anything that is currently set to No users or Not available.

  4. Block these MCP servers for the whole organization: [list items, for example Google Drive MCP, Google Calendar]. Show me the linked plugins and connectors before confirming each block.

  5. After each change, confirm the success message on screen. Keep a Word report of every action with the previous and new setting, and list anything you could not change.

Three tips make prompts like this work well. Be explicit about what must stay off. Ask for a read-only inventory first. And ask for a report with before-and-after values, so you can roll back any single change.

Takeaways

Measure usage before blocking. Use security groups as the outer boundary, then assign tools to groups rather than to everyone. Use the Package Management API for inventory and blocking, but expect to finish group-based access in the admin center until Microsoft adds those operations. And keep a written record of every change, because the fastest way to undo a governance mistake is knowing exactly what you changed.
