I Hate Documenting Environment Settings, So I Let Copilot Cowork Do It

Nov 12, 2026 · Chad Cox

An admin guide to having Copilot Cowork document any admin center for you, from Entra ID and Intune to Defender, Exchange, SharePoint, Teams, Purview and Power Platform, checked against CISA, CIS, NIST and Zero Trust baselines and kept current on its own.

The confession

I’ll say it: I hate writing documentation. I like building things and fixing things. I don’t like spending an afternoon taking screenshots of an admin center and typing setting names into a Word table.

The first version is only half the job. Keeping it current is the worse half. Someone adds a Conditional Access policy, a sharing setting changes, a new admin role gets handed out, and the document is out of date. Then the next audit or the next tenant build turns up a document nobody trusts.

So I tried something different. I asked Copilot Cowork to do it for me. It worked well enough that I’ve turned it into this guide: how an admin can hand the documenting of almost any environment setting to Cowork, from Entra ID to Intune to Power Platform, and have it stay current on its own.

What this guide covers

  • What Cowork needs before it can read an admin center for you
  • The one-paragraph prompt that produces a full configuration document
  • Ready-to-use prompts for Entra ID, Defender, Intune, Exchange Online, SharePoint and OneDrive, Teams, Purview, Power Platform and the Microsoft 365 admin center
  • How each setting gets checked against CISA, CIS, NIST and Microsoft Zero Trust guidance
  • The least-privileged role to run it with (it isn’t Global Administrator)
  • How to schedule it and get an email when something drifts

The pattern isn’t limited to Microsoft 365. If you can open a settings page in Edge and read it, Cowork can document it: the Azure portal, Power BI, or a third-party SaaS admin console you’re signed in to. Change the portal name and the list of areas in the prompt.

Before you start: what Cowork needs

Cowork reads the admin center through Microsoft Edge on your own device, signed in as you. It has the same reach you do, never more. Put these in place first:

  • Cowork itself. Your account needs a Microsoft 365 Copilot licence and access to Cowork in your tenant.
  • Browser access turned on. It’s off by default. An admin enables it under Copilot > Settings > View all > Cowork settings > Allow browser access, and can limit it to a security group such as your admin group.
  • Cowork in a browser. Browser tasks aren’t supported in the desktop app or on mobile.
  • Microsoft Edge, signed in with the same work account. InPrivate and guest windows don’t work. If you manage Edge centrally, the CopilotCoworkToolActionsEnabled policy must allow Cowork to act in Edge.
  • A read-only role, activated. See the least-privilege section below. Global Reader covers almost everything.
  • Sign-in prompts. Conditional Access and MFA still apply. When a prompt appears, Cowork hands control back to you.

Every Cowork browser task is recorded in the unified audit log, so there’s a record of what it opened.

What I asked for

My prompt was basically one paragraph:

Log into the Entra admin portal and write up a document about every setting that is currently set. Write it as a tech document that’s easy for peers to follow to set up another environment. Call out any setting that doesn’t follow best practices like CISA, CIS, NIST and Microsoft, including Zero Trust. This is documentation only. Do not make any setting changes. For each setting, include the PowerShell cmdlet that can be used to set it.

That was it. Cowork opened the Entra admin center in the browser using my existing session and went through the tenant blade by blade. It only read pages and never clicked Save. Then it built the Word document directly in my OneDrive.

What came back

A formatted configuration baseline that a peer can follow from top to bottom. In my lab tenant, it covered:

  • Tenant identity and properties: licence tier, domains, security defaults
  • User settings, external collaboration and cross-tenant access defaults
  • Groups: general settings, expiration and naming policy
  • Device settings, plus user and admin consent for applications
  • Conditional Access: every policy (57 in my tenant), its state, and named locations
  • Authentication methods: policies, method settings and the registration campaign
  • Password protection, self-service password reset and on-premises integration
  • ID Protection: user risk and MFA registration policies
  • Roles and administrators: Global Administrator count and privileged assignments
  • Hybrid identity (Entra Connect) and diagnostic settings

That added up to 19 sections and 114 documented settings. Each one has its current value, a status, the baseline it was checked against, and the PowerShell to set it.

The PowerShell column is the part peers will love

Every section includes the Microsoft Graph PowerShell cmdlet that configures the setting, for example:

  • Update-MgPolicyAuthorizationPolicy for user and guest settings
  • New-MgIdentityConditionalAccessPolicy for Conditional Access
  • Update-MgPolicyAuthenticationMethodPolicy for authentication methods
  • Update-MgPolicyCrossTenantAccessPolicyDefault for cross-tenant access

So the document is more than a record. It’s a runbook for building the next environment.

Not just Entra ID: the whole Microsoft 365 estate

I started with Entra because identity is where most attacks begin. But the same prompt works in any Microsoft admin center Cowork can open. Defender, Intune, Exchange Online, SharePoint and OneDrive, Teams, Purview and Power Platform all have settings that drift, baselines that apply and PowerShell that configures them.

A few tips for going wider:

  • One document per workload. Each document stays readable, and a drift email can say exactly which workload changed.
  • Some settings are portal-only. Where there’s no cmdlet, the document should say “set in the portal” and give the navigation path, so a peer can still follow it.
  • Pair it with the free tools. CISA’s ScubaGear checks a tenant against the SCuBA baselines, and Microsoft365DSC exports configuration as code. Cowork can turn either output into a document people will actually read.

Example prompts for each workload

Each prompt below tells Cowork what to read. End every one of them with the same guardrails so the output is read-only, consistent and checked against the baselines.

The guardrails (add to every prompt)

This is documentation only: do not change, save or create anything in the portal. For every setting, give the current value; whether it is Aligned, Gap, Review or Info against CISA SCuBA, the CIS Microsoft 365 Foundations Benchmark, NIST and Microsoft Zero Trust guidance; and the PowerShell cmdlet that sets it (or “portal only” with the navigation path). Write it as a Word document a peer could follow to rebuild the configuration, and save it to my OneDrive.

Defender for Office 365

Open the Microsoft Defender portal and document every email and collaboration policy: preset security policies, anti-phishing, inbound and outbound anti-spam, anti-malware, Safe Links, Safe Attachments, quarantine policies and alert policies. Note which users and domains each policy applies to and which policy wins when they overlap.

Defender for Endpoint

Open the Microsoft Defender portal and document the endpoint settings: advanced features, device groups and remediation levels, automated investigation, attack surface reduction rules, tamper protection, EDR in block mode, indicators and onboarding status. Note which settings are delivered through Intune rather than the Defender portal.

Intune

Open the Intune admin center and document compliance policies, configuration profiles, endpoint security policies, security baselines, enrolment restrictions, Windows Autopilot profiles, Windows update rings, app protection policies and tenant administration settings. Include each policy’s assignments and exclusions.

Exchange Online

Open the Exchange admin center and document organisation settings, mailbox auditing, remote domains and automatic forwarding, mail flow rules, connectors, accepted domains, DKIM, and the SPF and DMARC records for each accepted domain.

SharePoint and OneDrive

Open the SharePoint admin center and document external sharing for SharePoint and OneDrive, default link type and permissions, guest access expiry, access control (unmanaged devices, idle session sign-out, network location), OneDrive sync restrictions, site creation and storage settings.

Teams

Open the Teams admin center and document external access, guest access, Teams settings (email into channels, third-party file storage), meeting policies and meeting settings, messaging policies, and app permission and setup policies. Show the global (org-wide default) policy and every custom policy with who it is assigned to.

Microsoft Purview

Open the Microsoft Purview portal and document audit (on or off, and retention), retention policies and labels, data loss prevention policies, sensitivity labels and label policies, and any insider risk or communication compliance policies. Note the scope and mode (test or enforced) of each policy.

Power Platform

Open the Power Platform admin center and document the environments (type, region, security group), data policies (DLP) and their connector groups, tenant settings such as who can create environments and trials, tenant isolation, and Copilot and AI settings.

Microsoft 365 admin center

Open the Microsoft 365 admin center and document the org settings: password expiration policy, idle session timeout, release preferences, Customer Lockbox, user-owned apps and services, Microsoft 365 on the web, calendar and Bookings sharing, and Copilot settings. Mark anything that can only be set in the portal.

The industry baselines: document your security posture, not just your settings

This was the part I cared about most. A list of settings tells you what is configured. It doesn’t tell you whether that’s a good idea.

Every setting in the document is tagged with one of four statuses:

Status What it means
Aligned Matches the recommended baseline
Gap Doesn’t follow one or more baselines and should be remediated
Review Depends on your environment. Make a deliberate decision and record why.
Info Informational. No baseline applies.

The baselines referenced are:

  • CISA SCuBA (Secure Cloud Business Applications) baselines, which cover Entra ID, Defender, Exchange Online, SharePoint and OneDrive, Teams, Power Platform and Power BI
  • CIS Microsoft 365 Foundations Benchmark
  • NIST SP 800-63B (digital identity and authentication), NIST SP 800-207 (Zero Trust architecture) and NIST SP 800-53 (security controls) for audit mapping
  • Microsoft guidance, including Zero Trust deployment guidance and Conditional Access best practices
  • Microsoft security baselines (for Intune, Windows, Defender for Endpoint and Edge) and Microsoft Secure Score recommendations
  • CIS benchmarks for Windows, plus the CIS Microsoft Intune for Windows benchmark for device configuration

In my tenant, that came out to 40 Gaps, 31 Review, 24 Aligned and 19 Info. The document also includes a prioritised remediation order. Some examples of the kind of findings it surfaced:

  • Most Conditional Access policies were still in report-only mode, so they weren’t actually enforcing anything.
  • There were far more Global Administrators than the “fewer than five” Microsoft recommends.
  • Self-service password reset was turned off.
  • Entra sign-in and audit logs weren’t being sent anywhere for long-term retention.

Why does this matter beyond tidiness? Because this is evidence. When security, audit, compliance or cyber insurance asks “how is identity configured and how does it compare to a recognised framework?”, you can hand over a dated document instead of starting from scratch. The “Review” items also give you a place to write down why you deviated from a baseline. That’s exactly what an auditor wants to see.

Note: The baseline mapping is a strong starting point, not a certified audit. Have your security team validate the findings against the exact benchmark versions your organisation follows.

Least privilege: you don’t need Global Administrator for this

I ran my first pass as a Global Administrator because that’s how I was signed in. But nothing in this process changes a setting. Every step is a read. That means the realistic, least-privileged way to run it is with Global Reader.

Global Reader is a built-in Entra role, but it isn’t limited to Entra. Microsoft describes it as able to read settings and administrative information across Microsoft 365 services without being able to take management actions. That covers the Entra blades, and it also gives read-only access to the Defender portal, Intune, Exchange, SharePoint, Teams and most of Purview.

What you’re doing Least privilege needed
Interactive run in the Entra admin center (what Cowork did) Global Reader (Entra role)
Narrower option if you only document Conditional Access and ID Protection Security Reader
Reading diagnostic settings (log export) Global Reader for Entra. To check the destination workspace or storage, you also need Reader on the Azure subscription.
Scripted or unattended run through Microsoft Graph Read-only application permissions: Policy.Read.All, Directory.Read.All, RoleManagement.Read.Directory, Organization.Read.All
Defender XDR and Defender for Office 365 (portal) Global Reader, or Security Reader
Intune (devices, compliance, configuration, security baselines) Global Reader, or the Intune Read Only Operator role
Exchange Online, SharePoint and OneDrive, Teams, Microsoft 365 admin center Global Reader
Microsoft Purview (audit, retention, DLP, sensitivity labels) Global Reader for most pages. Some pages need a view-only Purview role group.
Power Platform (DLP policies, tenant and environment settings) Test Global Reader first. Some settings may need Power Platform Administrator or an environment-level role.

A few honest caveats:

  • Activate it with PIM. If you use Privileged Identity Management, make Global Reader an eligible assignment and activate it for the run. Don’t keep it standing.
  • Some values are hidden in the portal. These include group lifetime and smart lockout thresholds, and they were hidden even for a Global Administrator. The document flags them as “masked” rather than guessing.
  • Test with your own account. Before you rely on Global Reader, do one run with it to confirm it can see every blade your tenant uses.
  • Know the gaps. Microsoft documents a few places where Global Reader can’t yet see everything. Power Platform is the one most likely to need a different role. Check the current list before you rely on it.

Set it and forget it: make it run on its own

Writing the document once saves an afternoon. The bigger win is never having to think about keeping it current.

Cowork can run the same prompt on a schedule. For example: “On the first Monday of every month, capture the configuration baseline for Entra ID, Defender, Intune, Exchange Online, SharePoint and Teams, one document per workload, and save them to my OneDrive.” Each run produces fresh, dated versions, so the documentation is never more than a month old.

Drift detection: email yourself what changed

This is where it gets useful. Save each run to OneDrive or to a SharePoint library with versioning turned on. Then add one more instruction to the scheduled prompt:

Compare this run with the previous version in my OneDrive (or SharePoint) folder. If any setting changed, a policy was added or removed, or a status moved from Aligned to Gap, email me a summary of the differences. If nothing changed, send a one-line “no drift” email.

Now you get a short email that says something like “Conditional Access policy X was switched from Report-only to On” or “two new Global Administrators were added since last month.” You don’t have to remember to check. The change comes to you.

That helps in three ways:

  • Change control. Unplanned changes show up within a cycle, not at the next audit.
  • Security. A new Global Administrator, a relaxed consent setting or a disabled policy is exactly the kind of drift you want to know about early.
  • Audit history. The version history in OneDrive or SharePoint becomes a dated record of your posture over time.

Tip: Store the baselines in a SharePoint library that your team owns rather than in a personal OneDrive. That way the history survives role changes, and peers can find the current version.

Why this is a good Copilot Cowork use case

This isn’t a “summarise my email” task. It’s real admin work with a lot of steps:

  • It does the tedious part. It opens dozens of blades, reads every value and records it.
  • It adds judgement. It maps each setting to industry baselines and orders the remediation.
  • It produces a real deliverable. You get a formatted Word document in OneDrive that peers can use, not a chat reply you have to copy and paste.
  • It respects boundaries. “Documentation only, make no changes” is followed, and the process works with a read-only role.
  • It can repeat on its own. A schedule plus a drift email turns a one-time document into ongoing configuration monitoring.

Try it yourself

  1. Activate Global Reader (through PIM if you use it).
  2. Open Copilot Cowork in the browser and give it the prompt from the top of this post. Swap in the admin center you want (Entra, Defender, Intune, Exchange, SharePoint, Teams, Purview or Power Platform), and keep the line “do not make any setting changes”.
  3. Review the document, especially the Gap and Review items, and add your reasons for any intentional deviations.
  4. Save it to a team SharePoint library.
  5. Schedule a monthly re-run with the drift-email instruction.

I still hate writing documentation. Now I don’t have to, and it stays up to date on its own.
